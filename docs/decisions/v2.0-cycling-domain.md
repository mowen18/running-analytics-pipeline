# Revision v2.0 — 2026-08-18 — Cycling domain admission (purpose-level revision)

Status: Draft — pending owner approval.
Major version: this revision revisits the project's purpose (the v1.9
standard for touching the non-goals list), so it is v2.0, not v1.10.

## Rationale

The owner now cycles and wants the same pipeline discipline applied to
cycling questions. Four facts shape the scope:

1. Ingestion is already sport-agnostic. Rides have been landing in
   `raw_strava.activities` since `SYNC_START_DATE`; only the downstream
   filter (`int_runs_with_weather`) is run-specific.
2. Ride-level speed-at-HR is a weak efficiency signal. Wind, drafting,
   coasting, and terrain move it more than fitness does. A fixed Strava
   segment holds the course constant, so effort time at comparable HR
   on the same segment is the controlled cycling analog of the D10
   question.
3. The owner has a cadence sensor and no power meter. Cadence is
   therefore a first-class field; Strava's estimated power is not data
   this project will model.
4. On a fixed segment, wind is the largest remaining condition
   variable. The warehouse already stores wind speed; adding direction
   turns it into an explanatory headwind component per effort. The
   owner prioritized this over stream-derived rolling-speed metrics,
   which are deferred.

One governance clarification rides along. Decisions remain modifiable
at any time; what they are not is silently skippable. The §2 preamble
gains a sentence saying exactly that.

## What changes

### 1. Purpose (§1)

The project becomes an endurance-analytics pipeline with two peer
domains. The running thesis and its primary question are unchanged.
The cycling domain adds its own primary question:

> On fixed segments, is effort time at comparable heart rate improving
> over time?

Ride-level volume and cadence trends are supporting context for that
question, exactly as weekly training context supports the running
question.

### 2. Non-goal rewording (§3)

"Replication of standard Strava screens" is replaced by:

> **Plain replication of standard Strava screens.** Data or views that
> exist in Strava may enter scope when the project materially improves
> their interpretability, accessibility, or analytical context —
> trend statistics, normalization, weather or HR context, or custom
> thresholds Strava does not offer. The admitting addendum must name
> the improvement.

Named improvements for the segment work admitted here, relative to
Strava's My Results table: per-segment rolling median and cumulative
best; HR and cadence context on the trend; per-effort headwind and
crosswind components (D30); a noise caveat for short segments (D28).

### 3. Governance sentence (§2 preamble)

Appended: "Decisions bind the codebase between revisions; any decision
may be revised at any time by a recorded addendum — the record, not
permanence, is the point."

### 4. New decisions

| # | Decision | Final value |
|---|----------|-------------|
| D23 | Ride grain | `sport_type in ('Ride', 'MountainBikeRide', 'GravelRide', 'VirtualRide')`, configurable via dbt var `ride_sport_types`. `EBikeRide` and `EMountainBikeRide` are excluded from the domain: motor assist breaks HR-effort comparability. `VirtualRide` stays in the grain, flagged indoor, never weather-matched (mirrors `VirtualRun`). |
| D24 | Segment-effort ingestion | Per-ride detail fetch: `GET /activities/{id}?include_all_efforts=true` (owner-only endpoint). New raw tables: `raw_strava.activity_details` (one status row per attempted fetch: success / failed / unavailable; absent = not attempted — mirrors `raw_strava.streams`), `raw_strava.segment_efforts` (one row per effort: `effort_id` PK, `activity_id`, `segment_id`, payload JSONB, `fetched_at`), `raw_strava.segments` (one row per segment, payload upserted from the nested summary). Fetch gate: D23 ride types within the historical window. Batch cap `SEGMENT_FETCH_MAX_ACTIVITIES_PER_RUN` (default 50); exit-3 rate-limit contract as elsewhere. CLI/Make target: `sync-segment-efforts`. |
| D25 | Ride validity | Data-validity rules only (the v1.1 philosophy; no intensity gating): moving time ≥ 15 min; average speed within 3–35 mph sanity bounds (dbt vars); average HR within 90–200 bpm when present. HR is required only for HR-based aggregates, never for the grain or for time/speed/cadence trends. Invalid rides carry an exclusion reason, never a silent filter. |
| D26 | Cadence | First-class field (crank rpm) at ride and segment-effort grain wherever the source provides it. Missing stays NULL, never zero. Stream-grain cadence arrives only if the deferred ride-stream work enters scope. |
| D27 | Power exclusion | No power field is modeled anywhere in the cycling domain while `device_watts` is false. Estimated `average_watts` and `kilojoules` remain available only inside raw JSONB payloads. Revisited only by addendum if a direct-measure power meter appears. |
| D28 | Segment trend definition | Grain: segment × effort. Primary series: elapsed time; moving time secondary. Per-segment rolling median over the last **5 efforts** (`segment_rolling_effort_window`) and cumulative best. Trend display requires ≥ **5 total efforts** (`segment_trend_min_efforts`, the D12 spirit). Segments with median effort duration < **120 s** (`short_segment_seconds`) carry a displayed `short_segment` noise flag — ±1 s GPS sampling is material at that length — but are never excluded. Efforts from `VirtualRide` activities are excluded from segment marts; core keeps them with a flag. |
| D29 | Wind-direction ingestion | `raw_weather.hourly` gains `wind_direction_deg` (numeric, 0–360, meteorological convention: the direction the wind blows FROM; 0 legitimately means north — missing is NULL, never zero). Sourced from Open-Meteo hourly `wind_direction_10m` alongside the existing variables. Idempotent column addition in `sql/` applied by `make bootstrap`. The cache-completeness check gains the column so pre-migration rows are not frozen as complete; a one-time `make reconcile-weather` backfill populates history through the existing `IS DISTINCT FROM` upsert, within `WEATHER_REQUEST_BUDGET` (resumable across runs by cache design). |
| D30 | Headwind component | Segment bearing = great-circle initial bearing from the segment's `start_latlng` to `end_latlng` (both already in `raw_strava.segments` payloads). Sinuosity = segment `distance_m` / straight-line distance; segments above `winding_sinuosity_max` (default **1.3**) carry a displayed `winding_segment` flag — the straight-line bearing misdescribes them — but are never excluded. Per effort, wind = the nearest hourly observation at the parent ride's start cell to the **effort's** start time (60-minute rule; the hourly rows are already cached for the day). `headwind_mph = wind_speed_mph × cos(wind_direction_deg − bearing_deg)`; **sign convention: positive = headwind** (documented in README and dbt YAML, the D17 pattern). `crosswind_mph = wind_speed_mph × |sin(...)|` is secondary. NULL when direction is missing; computed and flagged, not nulled, when winding. Spatial caveat documented: wind is observed at the ride's start cell, not the segment's location. |

### 5. Amended decisions

- **D8 (weather source & grain).** The hourly variable set gains wind
  direction (D29). Source, grain, and every existing variable are
  unchanged; existing rows keep their keys, and value revisions occur
  only through the documented reconcile path.
- **D19 (view cap).** Maximum becomes **5** Streamlit views: the three
  running views unchanged, plus **Cycling segments** and **Cycling
  training**. Marts-only rule, the table-level allow-list, and the
  pinned allow-list test are unchanged. The D22 precedent (nest rather
  than raise the cap) was considered and rejected: cycling content
  nested inside running views would misdescribe both domains. The
  allow-list grows by exactly the three marts named in Phases C1–C2
  (`mart_weekly_cycling`, `mart_ride_quality`, `mart_segment_trend`),
  each addition proven red before the app change. Phase C3 extends
  `mart_segment_trend` in place and adds no allow-list entry.

### 6. Phases and releases

Phases C1–C3 are added to the plan (full text in §"Cycling Domain
Phases"). C1 + C2 constitute **Release 2.0**; C3 (wind direction and
headwind context) is **Release 2.1**.

### 7. Deferred list additions (§3)

- Stream-derived rolling speed and stop-loss metrics (the ride branch
  of the D15 stream fetch gate, the idle-speed threshold,
  pedaling-time share); enters by addendum.
- Polyline-based segment bearing for winding segments (refines D30's
  straight-line bearing).
- Segment efforts for runs.
- Ride cardiac drift (coasting breaks the D16 halves comparison).
- Speed-at-HR-band on segments (the D22 analog).

## What does NOT change

- The running thesis, D1–D7, D9–D18, D20–D22, every running model,
  mart, view, and test. Running output is byte-identical. D15 in
  particular is untouched: no ride streams are fetched in any C-phase.
- Schemas (D3): the new raw tables live in `raw_strava`; the wind
  column is added to the existing `raw_weather.hourly`; no new schema.
- Run and ride weather matching (D7 and the 60-minute rule): the
  effort-hour wind match (D30) is an additive path, not a change to
  the existing activity-level match.
- The Habit Focus Observatory independence rule and D20.
- No power modeling anywhere (D27 makes this explicit).
- The decision-addendum process itself.

   `VirtualRide` present with the indoor flag.
3. Re-running `sync-segment-efforts` converges: no duplicate efforts,

4. Spot check: effort count and times for one known segment match the
   Strava My Results screen for August 2026.
5. Allow-list: three red-first proofs, one per new mart; the pinned
   test's frozenset matches the amended list exactly.
6. Every invalid ride and every excluded segment effort carries a
   human-readable reason.
7. Headwind sign fixtures: northbound travel with wind from due north
   yields `headwind_mph = wind_speed_mph`; wind from due south yields
   the negative; due-east wind yields headwind ≈ 0 with full
   crosswind.
8. After the reconcile backfill, every cached location-hour carries a
   wind direction or an explicit NULL; a 0° value survives as north,
   never coerced to missing.
9. The `winding_segment` flag flips exactly at `winding_sinuosity_max`
   on synthetic segment fixtures.
